# Dungeondraft's blueprint for a mapmaker without map types

Dungeondraft is a grid-first, layered, vector-plus-splat-map editor. It never asks for a "map type": every map is a size in grid squares (up to 200x200, default 256 px per 5 ft square), and every tool is always available ([New Map guide](https://dungeondraft-encyclopaedia.gitbook.io/guide/introduction/new-map-first-steps.md)). Its drawing tools fall into two families. The first is the terrain family (terrain splat, material, water, cave, path, pattern), where each tool paints a surface. The second is the structure family (building, wall, portal, roof, light), where geometry carries behaviour such as line-of-sight blocking. Objects sit on top as a scatter-and-place system sorted by numbered layers plus an Over/Under flag. The strongest lessons for our creator are as follows. Drop the map type and make the grid a pure display toggle (G), as Dungeondraft already does. Add a coloured-region (splat) terrain brush with intensity and smooth blending. Give every placed item an Over/Under flag inside a numbered layer. Make scatter size-aware, with min/max rotation and scale ranges. Store door positions as wall segment index plus distance. Give shapes edit points that stay editable. Export UVTT-compatible walls, doors and lights. The same sources are equally clear about where Dungeondraft stops. It is "for a hamlet", not a city, and it has no world-map vocabulary, so a map creator with no type choice must add scale-aware behaviour that Dungeondraft lacks. The evidence is uneven. No official manual was reachable, and the native file format and pack schemas are undocumented (see the gaps in each section). What follows rests on a community encyclopaedia, Megasploot's modding API reference, and tutorial sites.

## One map, no types: size, grid and always-on tools

Dungeondraft's New Map dialog offers a size template or custom width and height up to **200x200 squares**, a default scale of "1 square = 5 ft = 256 px", an asset-pack selection and a Map Wizard for random dungeons and caves. It never asks whether the map is a battlemap, city or world ([New Map](https://dungeondraft-encyclopaedia.gitbook.io/guide/introduction/new-map-first-steps.md)). Three "Disable feature" checkboxes exist but were not named in the source. The grid is a hideable overlay (**G**) with a default dotted style plus colour and opacity settings, and snapping is a separate toggle (**S**). An Alignment tool (**H**) works even when the grid is hidden, and a Custom Snap mod (off-grid and hex intervals) was bundled by default in 1.1.1.0, which suggests snapping variants were a long-standing demand ([Map Settings](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/settings-tab/map-settings.md); [Interface buttons](https://dungeondraft-encyclopaedia.gitbook.io/guide/introduction/new-map-first-steps/useful-interface-buttons.md); [Reddit mirror](https://axebps-redlib.hf.space/r/dungeondraft)). Whether Dungeondraft can create a map with no grid at all was not confirmed. Our owner's design (size only, all tools, grid shown or hidden) therefore matches Dungeondraft's actual structure. The one real difference is that Dungeondraft sizes in squares, so a world map ends up 200 squares across at best.

Dungeondraft's limits at larger scales are documented by users. It "really doesn't work well for anything beyond a collection of houses around a town square, like a hamlet", and it is rigid and grid-centred ([r/FantasyMaps mirror](https://reddit.rtrace.io/r/FantasyMaps/comments/1bzbjcd/what_tools_do_you_use_to_create_your_maps)). World maps go to Wonderdraft or Inkarnate, and city maps are weak everywhere, with a common workaround of a Watabou generator base plus Photoshop ([Tildes](https://tildes.net/~games.tabletop/1ec8/my_experience_making_maps_when_i_run_games_or_how_i_learned_to_start_worrying_and_hate_city_maps)). One user found Dungeondraft "oddly better for hex maps because of the snapping" ([ENWorld](https://www.enworld.org/threads/questions-on-map-making-software.685613/)). For us, the missing pieces at city and world scale are an arbitrary pixels-per-square (or units) setting, a scale label (5 ft, 50 ft, 1 mile), hex snapping, and an object layer that does not choke on thousands of items. Reported lag on huge Wonderdraft maps arises because every asset is individually editable ([Tildes](https://tildes.net/~games.tabletop/1ec8/my_experience_making_maps_when_i_run_games_or_how_i_learned_to_start_worrying_and_hate_city_maps)). Our PixiJS scene should therefore cull offscreen sprites and bake static layers when an item count passes a threshold. That recommendation is our inference, not a Dungeondraft finding.

Navigation conventions are worth copying exactly, because mapmakers arrive with muscle memory. Pan is wheel-drag or Space-drag, zoom is Ctrl/Cmd+wheel, and a zoom dropdown reaches 800% (keyboard to 4000%) ([Navigating](https://dungeondraft-encyclopaedia.gitbook.io/guide/introduction/new-map-first-steps/navigating-the-map.md)). Global shortcuts are Ctrl+Z / Ctrl+Y for undo and redo, Esc to back out, Delete or Backspace to delete, **X** to toggle to the previous tool, **R** for the ruler, **L** for lighting and **C** for compare levels. Brush size uses `[` and `]` or the wheel ([Shortcuts](https://dungeondraft-encyclopaedia.gitbook.io/guide/general-info/mouse-and-keyboard-shortcuts.md)). The Alt-to-erase convention is universal: Alt while using the building, cave, water, material and terrain brushes switches to erase mode ([Shortcuts](https://dungeondraft-encyclopaedia.gitbook.io/guide/general-info/mouse-and-keyboard-shortcuts.md)).

## Terrain-family tools and how each behaves

The **terrain brush** is the most important one for a type-less creator. It paints a background splat from up to 8 texture slots (4 by default, a button adds 4 more at a VRAM cost). Textures replace one another rather than stack, and an intensity slider controls how quickly a texture builds up under a held brush. A Smooth Blending toggle switches between an organic and a smooth look, and a Fill button covers the whole map. Swapping a slot's texture changes every existing painted instance. Biome presets refill the first four slots and cannot be undone ([Terrain Brush](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/terrain-tab/terrain-brush)). Terrain is the lowest layer, can be disabled entirely for a transparent-background export, and cannot be partly transparent, so holes need Patterns ([same](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/terrain-tab/terrain-brush)). The data model is a raster: splatImage holds slots 1-4 and splatImage2 slots 5-8, with a textures array per slot ([Terrain API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Terrain/)). Seamless terrain textures are expected to be about 2048x2048 ([Custom Assets Guide](https://github.com/Megasploot/Dungeondraft/wiki/Custom-Assets-Guide)). Our JSON-items model has no place for a raster, so we must either store the splat as a chunked or run-length-encoded channel image beside the JSON, or keep terrain as vector shapes with soft edges. Splat is what makes world and city maps (biomes, fields, districts) cheap, and we recommend it.

The **path tool** draws a long-strip texture along a polyline. It is used for roads, rivers, cliffs and fences, and since 1.1.1.1 all walls are also available as paths. Click places points, and right-click, double-click or Enter finishes. Ending on the start point closes a loop, Delete or Backspace removes the last point, and Shift after the first point makes curves. Settings are layer, width, smoothness (0 angular to 1 rounded), Over/Under relative to other paths, Block Light, and transitions In and Out (Hard, Faded, Grow/Shrink) ([Path Tool](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/terrain-tab/path-tool); [PathTool API](https://megasploot.github.io/DungeondraftModdingAPI/reference/PathTool/)). Draw direction flips which side of the texture is up, and path textures must loop left-right. Edit Points mode drags points, adds on click and removes on hover plus Delete. After placement the select tool can change style and layer but not width, smoothness or transitions, a clear usability gap we can avoid. A path stores EditPoints, Smoothness, FadeIn/FadeOut, Grow/Shrink, a width scale and BlockLight, and the smoothed curve is regenerated from the edit points ([Pathway API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Pathway/)). Rivers and roads in a world or city map are paths with Faded or Grow/Shrink ends.

The **pattern shape tool** fills a rectangle, circle or freeform polygon with a tiling texture and no walls, like a floor. It is hard-edged and does not blend with neighbours. It has per-shape layer, texture rotation, colour, opacity and an optional outline, all editable later with edit points in the select tool ([Pattern Shape Tool](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/design-tab/pattern-shape-tool); [dndungeon](https://dndungeon.com/blogs/faq/dungeondraft-pattern-fill-vs-building-tool)). It has no hole option, and users carve holes by drawing points in from the edge or use mods. A native holes (inner rings) feature would be an easy improvement for our district shapes. The **material brush** paints bordered organic materials (rock, grass, ice, lava) on selectable layers, merges same-material strokes, and has a Smooth button, but its own documentation author calls it messy ([Material Brush](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/terrain-tab/material-brush.md)). The **water brush** has brush or shape (rectangle, circle, freeform) modes, Alt-erase, shallow colour at edges, deep colour far from edges, blend distance and a border toggle. Water is transparent, and assets on a Below Water layer render tinted and slightly distorted ([Water Brush](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/terrain-tab/water-brush.md)). The data is a polygon mesh with DeepColor, ShallowColor, BlendDistance, BorderTexture and RippleTexture ([WaterMesh API](https://megasploot.github.io/DungeondraftModdingAPI/reference/WaterMesh/)). Reviewers complain there is no tool to "envelop" water, so lakes need hand-stacked patterns and foam paths, although one reseller page claims otherwise (sources conflict) ([dndungeon review snippet](https://blog.dndungeon.com/p/thoughts-on-dungeondraft); [groupfinder](https://groupfinder.eu/library/dungeondraft)).

The **cave brush** digs organic caves with automatic walls (Dig mode by drag, Blast Open mode by click), with Alt to undo. Style and colour apply to all caves in the map, and cave walls are wall type 2 in the data and are exported as wall data in UVTT ([Cave Brush](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/design-tab/cave-brush.md); [Wall API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Wall/)). Our elevation feature (painted or generated heights shown as hill shading with sea level) has no Dungeondraft counterpart in any source. It is our differentiator for world and region maps, and nothing here argues for changing it.

## Structure tools: building, wall, portal, roof, light

The **building tool** is the single feature reviewers praise most. Drawing rectangles, circles or polygons creates floor plus walls in one gesture, overlapping shapes merge into one outline, and a rectangle between two shapes becomes a hallway ([Design tools](https://encounterlibrary.com/dungeondraft-basics/design-tools/)). Rooms keep their own floor texture and colour after merging, but the building has a single wall type, so joining buildings with different walls converts all walls to the selected type unless the wall tool is used. Edit points appear on hover, drag to move and click at a wall midpoint to add. Moving a wall stretches the floor with it, and placing a door or window cuts the wall automatically ([groupfinder](https://groupfinder.eu/library/dungeondraft)). The reviewer verdict is that this is the fastest indoor battlemap workflow of any tool (via a search snippet, unverified) ([dndungeon](https://blog.dndungeon.com/p/thoughts-on-dungeondraft)). Our `room` and `building` tools should adopt: merge-on-overlap, room-keeps-its-own-floor, walls as a derived result of the outline, and edit points that move both floor and wall.

The **wall tool** draws freestanding or interior walls point to point, open or closed, with the same textures and colour as the building tool. Shift adds curves, Over/Under controls layering, and a shadow toggle exists. Reviewers find the point-by-point drafting "obnoxious" next to the building tool ([Design tools](https://encounterlibrary.com/dungeondraft-basics/design-tools/); [WallTool API](https://megasploot.github.io/DungeondraftModdingAPI/reference/WallTool/)). Wall data holds Points, Texture, Color, Type (Auto from building, Manual, Cave), Joint (Sharp, Bevel, Round), Loop, HasShadow, an EndTexture cap and the walls' owned portals. Thickness is not a setting and comes from the wall texture. In the select tool, Ctrl-drawing continues or merges walls, and Shift-clicking two walls offers Merge Walls ([Shortcuts](https://dungeondraft-encyclopaedia.gitbook.io/guide/general-info/mouse-and-keyboard-shortcuts.md); [Contextual Controls](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/select-tool/contextual-controls.md)).

**Portals** (doors, windows, gates, arches) come in two kinds. Anchored portals snap to a wall, cut an opening and have a 180-degree flip. Freestanding portals go anywhere at any angle. A Closed flag decides whether a portal blocks light ([Design tools](https://encounterlibrary.com/dungeondraft-basics/design-tools/); [PortalTool API](https://megasploot.github.io/DungeondraftModdingAPI/reference/PortalTool/)). The data-model lesson is that an anchored portal is stored as WallID, WallPointIndex (the point preceding it) and WallDistance along the segment, plus Radius (half-width) and Direction ([Portal API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Portal/)). That parametric position survives wall edits, which is exactly what we need so doors follow a moved room edge. Freestanding portals use WallID -1 and a separate level list. Dungeondraft's export does not distinguish windows from doors; Roll20 infers it from the closed flag (open portal means window) ([Roll20 forum](https://app.roll20.net/forum/permalink/11486700/)).

**Roofs** are drawn independently of buildings, in Quickbox (drag) or Manual (points) mode, with Gable, Hip and Dormer types, a width slider, texture, Over/Under, and global shading (sun direction and contrast) ([RoofTool API](https://megasploot.github.io/DungeondraftModdingAPI/reference/RoofTool/)). Roof geometry (ridge direction) was not documented. Because the roof is not derived from the building outline, roofs are a manual second step. The "Building a Fantasy City" video series (not retrievable) suggests roofs and houses are the city-making workflow. For a city, a building tool that auto-creates a roof and offers a hide-roofs toggle would beat Dungeondraft. The **light tool** has range, intensity, colour, shadows and a style choice. Walls and closed portals block light by default, and paths and objects block only if Block Light is set. The environment tool sets one ambient colour (white is none) ([Light Tool](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/effects-tab/light-tool.md); [Environment](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/effects-tab/environment.md)). Lighting is one deferred full-screen pass after the scene ([Level API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Level/)).

## Objects, scatter, layers and the asset-pack system

The **object tool** opens the pack library in a sidebar. A click places the selected asset with snap (on by default, **S**), a rotation slider (scroll wheel, Z+wheel for fine steps), a scale slider (Alt+wheel), Shift+wheel to cycle assets, **A** to mirror, and Shadow and Block Light toggles ([Object tools](https://encounterlibrary.com/dungeondraft-basics/object-tools/); [ObjectTool API](https://megasploot.github.io/DungeondraftModdingAPI/reference/ObjectTool/); [Shortcuts](https://dungeondraft-encyclopaedia.gitbook.io/guide/general-info/mouse-and-keyboard-shortcuts.md)). The **scatter tool** paints a stroke of randomised objects. It has min and max rotation and min and max scale (identical values give uniform results), a Spread value for density (negative values pack tightly; the dev blog says it is a grid-unit distance that accounts for object size), and a colour list that cycles randomly. Shift-click selects an asset range and Ctrl-click adds individual assets, all randomised together ([Object tools](https://encounterlibrary.com/dungeondraft-basics/object-tools/); [ScatterTool API](https://megasploot.github.io/DungeondraftModdingAPI/reference/ScatterTool/); [dev blog](https://kungiris.blogspot.com/2020/02/dungeondraft-progress-update-object.html)). A single click with scatter places one random item and re-rolls, which is useful for food on tables. We already have scatter with folder sets, each picture keeping its own size, so the gaps worth closing are the min/max ranges, size-aware negative spread, per-stroke undo grouping (inferred, not confirmed), and a click-once re-roll mode.

**Layers.** Dungeondraft has numbered user layers for patterns, materials, paths and objects only (default 100 "User Layer 1", 200 "User Layer 2", and so on, higher on top), plus named layers such as Above Walls, Above Roofs, Below Water and Below Ground, with hotkeys 1-4, 7, 9, Alt+1 and Alt+4 in 1.2.0.0+. Inside a layer, each item carries an Over/Under flag ([Layers & Sorting](https://dungeondraft-encyclopaedia.gitbook.io/guide/general-info/layers-and-sorting); [Objects API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Objects/)). The layer stack is fixed, and a "Manage Layers" mod exists to change it (search snippet) ([dndungeon mods](https://dndungeon.com/blogs/faq/best-dungeondraft-mods-2026)). The exact z-order was not documented anywhere reachable. Separately, **levels** are independent maps stacked as floors, each with its own settings and lights. They can be cloned, reordered by drag and switched with Page Up/Down, and a Compare Levels overlay shows a reference level beneath ([Level Settings](https://dungeondraft-encyclopaedia.gitbook.io/guide/all-the-tools/settings-tab/level-settings.md)). For us, "layers/variants" maps to Dungeondraft's levels (variants such as day/night or before/after), and the user-facing z-order should be a small, named list rather than editable numbers.

**Colourable objects.** Pixels that are red inside the source image are the recolourable region. Pack headers define thresholds (OverrideCustomColor, MinRedness, MinSaturation, RedTolerance), and a "colorable" tag filter and an eyedropper exist ([AssetPack API](https://megasploot.github.io/DungeondraftModdingAPI/reference/AssetPack/); [Object tools](https://encounterlibrary.com/dungeondraft-basics/object-tools/)). The exact algorithm and default thresholds are unknown. Forgotten Adventures assets are not red-keyed, so this mechanism does not apply to our packs. A plain multiply tint (or a hue shift) per item is the practical equivalent, with pre-coloured variants as the alternative that third parties use ([Mortality Plays](https://mortalityplays.itch.io/painterly-megapack)).

**Packs.** A `.dungeondraft_pack` is a single archive (believed to be a Godot PCK, unconfirmed) unpacked as `pack.json`, `textures/<kind>/` (caves, lights, materials, objects, paths, roofs, terrain, tilesets, walls) and `data/default.dungeondraft_tags`, which maps tag names to asset paths ([GoPackager](https://github.com/Ryex/Dungeondraft-GoPackager); [Rouberol](https://blog.balthazar-rouberol.com/cleaning-up-the-dungeondraft-tag-list); [ddraft-cmd-tool](https://pypi.org/project/ddraft-cmd-tool/)). Pack metadata includes Name, unique ID, Version, Author, Preview and Keywords. The library offers All, Used on this map, and Tags views, search with a Fuzzy/Exact slider, multi-select tags, and a tag-collections dropdown ([Object tools](https://encounterlibrary.com/dungeondraft-basics/object-tools/); [2 Minute Tabletop](https://2minutetabletop.com/beginners-guide-to-dungeondraft-custom-assets/)). Loading many packs slows or crashes the app, so users enable only what they need. Pack authors use 256 px per square ([PeaPu](https://peapu.gumroad.com/l/PeaPuModernCity1)), and Forgotten Adventures splits into Objects and Textures packs with about 30,000 objects on its largest tier ([Forgotten Adventures](https://new.forgotten-adventures.net/?p=3738)). A map records an AssetManifest of the packs it depends on, and the API can embed a PNG into the map file ([Header API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Header/); [ObjectTool API](https://megasploot.github.io/DungeondraftModdingAPI/reference/ObjectTool/)). Since we read FA zips directly, the lessons are the "Used on this map" view, the fuzzy/exact search, a per-map pack manifest in our JSON (so a missing pack shows a clear placeholder), and lazy-loading by pack to avoid Dungeondraft's slowdown.

## Data model and export: what to mirror in JSON

Dungeondraft's World holds a header and a list of Levels. Each Level owns **typed containers** (floor shapes, pattern shapes, cave mesh, terrain splat, water, walls with portals, pathways, objects, roofs, lights, texts, material meshes), not one flat list ([Level API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Level/); [World API](https://megasploot.github.io/DungeondraftModdingAPI/reference/World/)). Every placed node has an integer node_id, and mods are told to store IDs rather than references ([Serializing mod data](https://megasploot.github.io/DungeondraftModdingAPI/tutorials/SerializingModData/)). The World has a Format version, Width/Height in cells, GridSize, TileSize and default shadow settings. The header stores creation build and date and the pack manifest. The raw JSON key names, terrain encoding and layer numbers are not publicly documented. Our item-per-layer JSON already approximates this. Three worthwhile adoptions are stable integer IDs per item (so portals can reference walls), a `format` version number, and a pack manifest.

The **export** side is better documented. Image export offers PNG, JPEG, WEBP and Universal VTT, a default 256 px per square (max 300), a quality slider, crop, grid presets (Best Quality, Roll20), and visual options (grid, lighting, camera filter such as Printer-Friendly or Sepia, overlay-level export). Most VTTs reject images over 16384 px, and a chunked export exists for large maps ([Quality](https://dungeondraft-encyclopaedia.gitbook.io/guide/final-steps/exporting-your-map/quality-settings.md); [Visual](https://dungeondraft-encyclopaedia.gitbook.io/guide/final-steps/exporting-your-map/visual-settings.md); [Exporter API](https://megasploot.github.io/DungeondraftModdingAPI/reference/Exporter/)). The `.dd2vtt` format is JSON with `resolution` (`map_origin`, `map_size` in squares, `pixels_per_grid`), `line_of_sight` and `objects_line_of_sight` polylines, `portals[]` (position, bounds, rotation in radians, closed, freestanding), `environment` (baked lighting, ambient colour), `lights[]` (position, range, intensity, colour, shadows) and a base64 `image`, all in grid-square units ([Arkenforge UVTT](https://arkenforge.com/universal-vtt-files/)). The format is supported by Foundry, Roll20, MapTool, Fantasy Grounds Unity, Arkenforge, D20Pro and Encounter+ ([dungeondraft.net](https://dungeondraft.net)), so a Viewer-side UVTT export of our walls, doors and lights is the highest-value interoperability feature. Known pitfalls are that windows import as doors on Roll20 and light colour may or may not apply on import ([Roll20 forum](https://app.roll20.net/forum/permalink/11486700/)).

Several items deserve extra steps. For priority 7, because our items are JSON, choose between a chunked raster stored alongside the JSON and vector shapes with soft edges, and decide it before building elevation-style features that depend on it. Priority 6 also depends on the pack browser, since multi-select of folders is the main gesture. For the district tool, no Dungeondraft equivalent exists for city blocks; the closest is a pattern shape, so the district feature remains ours to design. The same is true for generated city blocks, which Dungeondraft does not attempt and which users fill from outside generators.

## What the sources could not tell us

The most important gaps are structural. No official manual was reachable. The native `.dungeondraft_map` JSON key names, terrain encoding, `pack.json` and tags schemas, and the pack container format were not found; the claim that the map file is "just JSON apart from terrain" is an unverified user comment ([MapMe request](https://mapme.productlift.dev/p/export-to-dungeondraft-map-file-format-9hXimu)). Layer z-values, the red-recolour algorithm and thresholds, roof geometry, default pixels per square for imports (256 is widely used but not officially confirmed), stairs and pillars (probably plain objects), wall thickness controls, copy/paste and prefab behaviour, and object flip and favourites were not documented. For community opinion, YouTube transcripts, Reddit threads and Steam or itch reviews were not retrievable, so hotkey tricks, beginner mistakes and a feature wishlist rest on release notes and search snippets. Several review quotes come from search snippets of a page that redirected on fetch, and the water-tool claim conflicts between sources. Release history is only known for 1.1.0.6 (Feb 2024), 1.1.1.0 (Oct 2024, hotbar, Custom Snap, text visibility per level) and 1.1.1.1 (about Mar 2025, languages, doors and windows as objects, walls as paths); 1.0.x, 1.1.0 and later releases are unknown. Pricing is $19.99 one-time per the official site, against older forum figures of $30. One reviewer's anecdotal rating of 4.2/5 is a small informal sample ([GummySearch](https://gummysearch.com/tools/best-products/map-making-software/)).

## Conclusion

The sharpest insight is that Dungeondraft is already type-less, so the owner's wish is a validation rather than a risk: the real differences between a battlemap, a city and a world are scale, density and which layers are populated, not which tools exist. What Dungeondraft lacks is exactly what we can add on top: unit scale, large-map performance, auto roofs, district-level tools and elevation. Its best ideas are small and structural: Over/Under within named layers, parametric doors on walls, edit points everywhere, a splat terrain brush and size-aware scatter. They are cheaper and more valuable than any single flashy tool.

Two pieces of follow-up would reduce the remaining uncertainty. Opening a real `.dungeondraft_map` file would settle the native format and layer numbers, and the in-app shortcut list or the unofficial manual would settle the hotkeys that sources left silent. Neither should block the first five priorities, which are fully defined by the evidence above.
